# ADR 0033 (번호는 병합 때 다시 매길 수 있음) — 그림 v2: 기본 세트 정리·As-Is/To-Be·분석 기법 추천·인포그래픽 프롬프트 (2026-10-28, 레인 C)

## 배경
시범 운영 첫날 의견: (1) 자동으로 넣은 개념도·체계도·로드맵은 글자가 작고 본문을 되풀이한다. (2) Nano Banana Pro 그림이 회색 밑그림을
그대로 베낀 모양이라 빈 곳이 크다(ADR 0029 프롬프트의 "참고 이미지 배치 그대로 유지"). (3) 심사자가 한눈에 보는 "현재 → 연구 후" 그림과,
제안 내용을 SWOT·퓨 매트릭스·비용-편익 같은 분석 틀로 정리한 그림이 있으면 좋겠다.

## 선택지
1. 기존 6종 유지 + 프롬프트만 개선 — 본문 되풀이 문제는 그대로.
2. 기법 그림을 앱 규칙으로 고르기(키워드) — 맞지 않는 기법을 억지로 넣는다.
3. **기본 세트를 As-Is/To-Be + 조건부(수치 그래프·일정표)로 줄이고, 분석 기법은 Argon 이 이 제안에 의미 있는 것만 0~2개 골라 실제로
   분석한 결과를 명세로 받아 그린다.** 맞는 기법이 없으면 "해당 없음"(사유)으로 끝낸다.

## 결정
- 3번. 기본 그림 = `as_is_to_be`(2-나 연구목적, 비면 2-가-(2)) → `stat_chart`(검증 수치) → `schedule`(연구기간) + 분석 기법 추천
  `technique_slots`(남은 자리, 최대 2) — 합쳐 최대 4장. 개념도·체계도·로드맵·비교는 [다른 그림 추가]에서만(`figures.yaml auto_kinds`).
  양식에 "연구배경 및 필요성" 칸이 없어 As-Is/To-Be 는 `objective` 에 붙인다.
- As-Is/To-Be 명세: 쪽마다 3~4칸(이름표 현황·원인·한계 / 목표·해결 방안·기대효과, 다듬기가 자리대로 맞춤) + 가운데 화살표 한 줄. 글자는
  입력·초안·인용 근거에서만(`validate_spec`). 밑그림은 왼쪽 점선·빗금(회색·주황), 오른쪽 굵은 실선·점(파랑·초록) — 흑백에서도 구분.
- 분석 기법 20종 `config/figures/techniques.yaml`(핵심 내용·적합한 상황·묶음·척도·칸). 고르기·분석은 Argon(review provider, 예산 래퍼) 먼저,
  실패면 로컬, 모델마다 교정 1회(`TechniqueSteps`). 종류별 규칙(`domain/rules/techniques.py`): 정성 = 고정 묶음 + 강도 상·중·하,
  비교·평가 = 열×기준 표 + 척도 기호(+/0/− 또는 상·중·하), 경제성 = 금액은 제안·근거에 그대로 있는 수치만(아니면 "산출 필요", 새로
  계산하지 않음), 연구 절차(델파이·문헌고찰) = 등급 없음. 모든 기법 그림에 "제안 내용 기반 예비 평가". 항목마다 출처(문장 id·근거 id·
  입력 칸)를 남기고 카드 "항목 출처"로 보인다(내부 id 대신 "2-다 … 문장 1"·"제안 입력: 발생 원인"·"근거 자료").
- 추천 그림은 `Figure.recommendation{technique, reason, status pending|accepted|dismissed, swapped_from}`. 카드 [넣기 확정]·[필요 없음]
  (섹션 아래 접힘, 다시 넣기)·[다른 기법으로 바꾸기](같은 자리, 다시 결정 전). 모두 새 버전이고 `figure_diff` 에 accepted·dismissed·
  restored·swapped 로 한 건씩 잡힌다(버전 비교 "변경 n건"). 결정 전 추천은 제출 전 점검 "결정 전 추천 그림", 그대로 마무리하면 들어간다.
- 빈 결과도 사유: `RunState.figure_techniques{status: recommended|none|failed|filtered|off, reason, picks, dropped}` → 화면 "분석 기법
  추천: 해당 없음 — <사유>" + [다시 시도](`POST /v1/runs/{id}/figures/techniques`, 이미 있는 기법은 빼고 남은 자리만).
- 그림 프롬프트(`image_prompt`): "밑그림은 내용 구조만 — 새로 디자인"(제목 계층·색 강조·일반 아이콘·고른 여백·큰 글씨·흑백 구분),
  글자 목록 그대로·더하지 않기 유지, 그래프·일정표만 값·기간 비율 유지. 제목 글자가 목록에 없는 종류는 "제목을 새로 쓰지 않는다"
  (첫 실측에서 "… 인포그래픽" 제목을 지어 씀). 비율은 내용 양(`choose_aspect`: 21:9·16:9·3:2·4:3), 밑그림·그림 생성이 같은 비율.
  상자 글자는 새 명세에서 30자(`MAX_BOX`, 1~2줄)로 줄인다(저장된 명세는 그대로 읽힌다).
- 공용 계정 run(scope public)은 기법 프롬프트·출처·pool 에서 internal 청크를 뺀다. 캡션 12pt·가운데 정렬은 레인 D 의 HWPX 작업에 맡긴다.

## 결과 (2026-10-28 오후)
- 측정 `docs/eval-2026-10-28-figures-v2.md` — 같은 명세 6종 기존/v2 프롬프트 나란히, Argon 추천 1회(퓨·SWOT, 텍스트 3회·64초).
- 테스트: 백엔드 +37(규칙 13·유스케이스 12·RunManager 6·REST 3·밑그림 3, 기존 테스트 갱신), vitest +7(추천 카드, axe 0), e2e 1 추가·2 갱신.

## 후속
- Nano Banana 가 큰 글씨로 그리며 일부 글자가 뭉개지는 경우(As-Is/To-Be 2회차 "센서"·"한계")가 있다 — 확인 전 배지·제출 전 점검으로 잡고,
  필요하면 [기본 그림으로]. 글자 정확도 OCR 대조는 여전히 하지 않는다(ADR 0029).
- 골든셋에서 기법 추천률·"해당 없음" 비율·제안자 결정(넣기 확정/필요 없음) 비율을 잰다(`rra eval` 열 추가는 후속).
