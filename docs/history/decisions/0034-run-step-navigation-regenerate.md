# ADR 0034 — 위쪽 단계 표시로 ①·② 를 다시 열고, 바뀐 입력은 관련 섹션만(또는 전체) 새 버전으로 다시 쓴다 (2026-10-28)

> 레인 D(feat/format-ui). 번호는 합칠 때 다른 레인과 겹치면 다시 매긴다.

## 배경
시범 사용자는 초안을 본 뒤 아이디어·정책 근거·차별화 방향을 고치고 싶어 했지만, ①·② 화면은 새 제안서(/new)에만 있어 새 run 을
처음부터 다시 만들어야 했다(검색·작성·검토 시간 전부). 위쪽 단계 표시(①~⑥)는 보기만 되고 눌리지 않았다.

## 선택지
1. 새 run 으로 다시 생성 — 이전 초안·편집·검토가 다른 run 에 흩어진다.
2. **같은 run 안에서 입력을 바꾸고, 저장할 때 [보기만 하고 돌아가기] / [바뀐 내용과 관련된 섹션만 다시 쓰기(새 버전)] /
   [초안 전체 다시 생성(새 버전, 기존은 이전 버전으로 보존)] 중 고른다.**
3. 입력을 바꾸면 자동으로 전체 재생성 — 제안자가 고친 문장이 사라지고 호출이 늘어난다.

## 결정
2.
- 규칙 `domain/rules/request_change.py`: 바뀐 입력 칸 → 그 칸을 읽는 섹션(프롬프트 기준). 문제 정의 4칸·보충 정보는 전체,
  가제 → 연구과제명, 제약 → 연구 방법·활용계획, 정책 근거 → 정책적 중요도·전략 정합성, 활용 부서 → 기대효과 3·활용계획,
  특이사항 메모 → 특이사항, 차별화 방향 → 목적·방법·특이사항, ② 우선 근거 → 근거 필수 섹션, 제안부서·예산 → 없음(입력만 저장).
- `RunManager.regenerate(mode=sections|all)`: 생성과 같은 작성 길(Argon 먼저·실패면 로컬, 로컬은 슬롯 안, Argon 은 run 칸 +
  `compose.concurrency`). sections 는 U3 다시 쓰기 길이라 제안자 수정·입력 문장과 앱 문장은 그 자리에 둔다. all 은 모든 섹션을
  새로 쓰고 이전 초안은 이전 버전으로 남는다(`origin=regenerate`, note 에 바뀐 칸 이름). run 을 claim 해 생성·검토와 겹치지
  않게, 기준 버전이 바뀌면 409.
- **근거는 다시 검색하지 않는다** — 처음 검색 집합 안에서만(보안 A 대조 집합 유지, 이전 버전의 근거 id 도 계속 풀린다). 우선 근거는
  그 집합 안의 것만 앞세운다. 입력을 크게 바꿨다면 새 제안서를 권한다(대화 상자 안내).
- 다시 쓰지 못한 섹션은 이전 내용을 두고 `failed` 로 알린다(빈칸으로 덮지 않음). 전부 실패면 아무것도 저장하지 않는다.
- REST: `GET /v1/runs/{id}/request`, `POST …/request/preview`, `POST …/regenerate`. 웹: 단계 표시가 run 안에서 눌리고(닿지 않은
  단계는 이유 표시), `/runs/:id/idea`·`/runs/:id/precheck` 가 저장된 입력으로 ①·② 를 연다.
- 설계도(Q2)는 다시 만들지 않는다(옛 입력 기준 설계도가 새 입력을 끌고 가지 않게, all 에서도 설계도 없이).

## 이유
- 편집·검토 기록이 한 run 에 남고, 바뀐 만큼만 호출한다.
- 같은 작성 길을 써서 전송 범위·검증·대체 규칙이 생성과 같다.

## 결과
- 가짜 LLM 테스트: 관련 섹션만 새 버전, 제안자 수정 보존, 전체 다시 생성 시 이전 버전 보존, 실패 섹션 유지, 충돌 409·실행 중 409.
- 남은 것: 실제 Argon 으로 관련 섹션 다시 쓰기 시간(섹션 수에 비례, 4개씩 동시) 측정. 화면은 동기 호출이라 섹션이 많으면 1분 안팎.
